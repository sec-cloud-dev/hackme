# fuzzpool — распределённый фаззинг с оплатой только за проверенный результат

Это прототип на Go (только стандартная библиотека). Он показывает, как может выглядеть
основа сети, где люди отдают вычислительную мощность под фаззинг, а заказчики платят
за найденные баги. Прототип написан как разбор того, чего не хватает
[HackMe Network](https://github.com/jokeez/hackme), и сделан как рабочий код с тестами, а не как список претензий.

## Главная идея

**Воркер ничего не заявляет. Он присылает входные данные.**

Координатор сам прогоняет каждый присланный вход на закреплённой (по sha256) сборке цели
и платит только за то, что измерил сам:

| За что платим | Как координатор это проверяет |
|---|---|
| Новые рёбра покрытия | прогоняет вход через `afl-showmap` и сравнивает с общей картой покрытия кампании |
| Новый уникальный краш | прогоняет вход **дважды** под ASan/UBSan/MSan; сигнатура (тип + верхние кадры стека) должна совпасть и быть новой |

В протоколе **нет** полей «хешрейт», «попытки», «exec/s», «время работы», «edges_touched».
Неизвестные поля JSON отклоняются, поэтому прислать такое «утверждение» невозможно даже технически.

**Деньги не печатаются.** Своей монеты нет. Всё, что получают воркеры, заранее положил
в эскроу заказчик. Бухгалтерия ведётся двойной записью в целых микроединицах, сумма всех
счетов всегда равна нулю, и это проверяется повторным проигрыванием журнала.

## Чем это отличается от HackMe (rc17.3)

Ссылки ведут на код HackMe в состоянии на 2026-10-21.

| Вопрос | HackMe | fuzzpool |
|---|---|---|
| Откуда берутся деньги | Эмиссия HMC за блоки «PoH»: найти `n`, где `(7n+13) mod M = 0` (`internal/chain/retarget.go:64`). Это решается формулой за микросекунды. При запуске создано 50 000 HMC на адрес оператора (`internal/block/genesis.go:11`) | Своей монеты нет. Платит только эскроу заказчика |
| За что платят майнерам | За «попытки», ограниченные заявленным клиентом `hashrate_gh_s` (`cmd/coordinator/work.go:1997–2045`). Режим «платить только за находки» по умолчанию выключен (`work.go:309`) | Только за новые рёбра и новые краши, которые координатор измерил сам |
| «Чистые» прогоны фаззинга | Оплачиваются. Полностью перепроверяется только выборка: Hunt 100%, Deep 40%, Audit 5%, Scan 1% (`internal/poolfuzz/replay_policy.go`), плюс 2% «канареек» с подложенным багом (`canary.go`). Пойманная подделка просто отклоняется, залога и штрафа нет. Остальное проходит по порогам на заявленные `duration_ms` / `edges_touched` (`clean_floor.go`) | Прогона «без результата» не существует: не нашёл нового — не заработал. Ложное заявление стоит залога |
| Представление денег | `float64` в API и расчётах выплат | `int64` микроединиц; в JSON только строки, число с плавающей точкой отклоняется |
| Идентификатор участника | 64 бита (`HMC-` + 16 hex, `internal/nodecrypto/ed25519.go:114`) | Полный SHA-256 от ключа Ed25519 (256 бит) |
| Повтор и подделка запросов | Ed25519 | Ed25519 + разделение доменов подписи + строго растущий nonce на воркера |
| Изоляция | bwrap заявлен для Hunt | bwrap на **обеих** сторонах: у воркера (чужой код заказчика) и у координатора (чужие входы). Тест проверяет, что внутри нет сети, не виден `$HOME`, не утекают переменные окружения и `/usr` только для чтения |
| Структура | `main.go` 181 КБ, `pool.go` 85 КБ, 130+ файлов в корневом пакете | 9 небольших пакетов, у каждого одна ответственность |

## Как это работает

```
заказчик ──оплата──▶ ledger: customer → escrow   (5% платформе, раскрыто заранее)
                                │
воркер ──подписанный запрос──▶ КООРДИНАТОР ──лиза: цель (sha256), цены, общий корпус──▶ воркер
                                                                                           │
                               libFuzzer / AFL++ / демо-мутатор в bwrap ◀──────────────────┘
                                                                                           │
воркер ──подписанная пачка входов (≤64)──▶ КООРДИНАТОР ◀───────────────────────────────────┘
   для каждого входа, в песочнице, на закреплённой сборке:
   ├─ падает?               → повторить; сигнатура совпала? новая → платим за краш, иначе 0
   ├─ заявлен краш, но не падает → штраф из залога воркера в эскроу заказчика
   └─ не падает             → afl-showmap → новые рёбра? платим цена×рёбра, иначе 0
   выплата: escrow → кошелёк воркера, не больше остатка эскроу; эскроу пуст → кампания закрыта
```

Почему **залог** (stake): проверка краша — самая дорогая операция. Ложное заявление
стоит воркеру денег, а сам залог делает дорогим спам с тысяч фиктивных аккаунтов.
Штраф уходит в эскроу заказчика и компенсирует впустую потраченную проверку.

Почему **общий корпус в лизе**: каждый воркер начинает с уже проверенного прогресса
всех остальных. Украсть чужой вход и прислать его повторно бесполезно: покрытие уже засчитано.

Почему **базис заказчика бесплатный**: сиды, которые заказчик дал при создании кампании,
прогоняются заранее. Воркеры получают деньги только за то, что вышло **за** этот уровень.

## Пакеты

| Пакет | Что делает |
|---|---|
| `internal/money` | Сумма = `int64` микроединиц, разбор и вывод строк, проверка переполнения |
| `internal/ledger` | Журнал двойной записи, `TransferUpTo` для выплат из эскроу, `CheckInvariant` |
| `internal/identity` | Ключи Ed25519, ID = SHA-256 ключа, подписи с доменом |
| `internal/coverage` | Карта рёбер, вычисление новизны |
| `internal/target` | Интерфейс `Executor`, разбор отчётов ASan/UBSan/MSan/libFuzzer и `afl-showmap`, исполнитель реального бинарника, демо-цель `TinyParse` с двумя заложенными багами |
| `internal/sandbox` | Обёртка bubblewrap: все пространства имён отделены, система только для чтения, лимит CPU |
| `internal/protocol` | Формат обмена; намеренно без полей с самоотчётом |
| `internal/coordinator` | Кампании, лизы, проверка, выплаты, штрафы, HTTP API |
| `internal/worker` | Клиент, движки: демо-мутатор, libFuzzer, AFL++ |

## Запуск

Нужно: Go 1.26+, Linux. Для изоляции нужен `bwrap`, для реальных целей — AFL++ и clang.

```bash
go test -race ./...     # все тесты, включая реальную изоляцию bwrap и гонки воркеров
go run ./cmd/demo       # полная кампания: честный воркер зарабатывает, мошенник пробует 6 трюков
```

Пример вывода демо (сокращён):

```

    раунд 1: отправлено входов 11 → новых рёбер 10, новых крашей 2, выплачено 45.000000
[3] Мошенник 7f262b64…
    а) заявил «hashrate_gh_s: 1700»        → отклонено: HTTP 400 json: unknown field "hashrate_gh_s"
    б) переотправил чужой корпус           → выплачено 0.000000, вердикты: no_new_coverage×10
    в) повторил принятый подписанный запрос → отклонено: HTTP 409 stale nonce
    г) подписал от имени другого воркера    → отклонено: HTTP 401 bad signature
    д) сдал работу по чужой лизе            → отклонено: HTTP 403
```

### Координатор и воркер вручную (демо-цель)

```bash
FUZZPOOL_ADMIN_TOKEN=secret go run ./cmd/coordinator -listen 127.0.0.1:8090
H='Authorization: Bearer secret'
curl -XPOST localhost:8090/v1/admin/deposits  -H "$H" -d '{"account":"customer:acme","amount":"100"}'
curl -XPOST localhost:8090/v1/admin/campaigns -H "$H" -d '{"name":"demo","customer":"customer:acme",
  "budget":"100","price_per_edge":"0.5","price_per_crash":"20","target":"tinyparse","seeds":["RloBAA=="]}'
go run ./cmd/worker -engine demo        # печатает stake-счёт, который нужно пополнить
curl -XPOST localhost:8090/v1/admin/deposits  -H "$H" -d '{"account":"stake:<id>","amount":"5"}'
go run ./cmd/worker -engine demo -rounds 2
curl localhost:8090/v1/ledger/invariant
```

### Реальная цель (C/C++)

```bash
# сборка для проверки на координаторе и для воркеров AFL++: инструментирована AFL, ASan, драйвер libFuzzer-совместимый
afl-clang-fast -g -fsanitize=address,fuzzer harness.c -o target
# необязательная сборка для воркеров libFuzzer
clang -g -fsanitize=address,fuzzer harness.c -o target-lf

FUZZPOOL_ADMIN_TOKEN=secret go run ./cmd/coordinator \
  -target-bin ./target -showmap "$(command -v afl-showmap)" -libfuzzer-build ./target-lf
go run ./cmd/worker -engine aflpp     -binary ./target    -duration 10m
go run ./cmd/worker -engine libfuzzer -binary ./target-lf -duration 10m
```

Лиза закрепляет sha256 каждой сборки, и воркер откажется фаззить не ту.
Ограничивайте память цели через cgroup (`systemd-run --scope -p MemoryMax=2G …`), а не через
`RLIMIT_AS`: ASan резервирует терабайты виртуальной памяти и с `RLIMIT_AS` не запускается.

## Что проверено и что нет

Проверено тестами (`go test -race ./...`, все проходят):

- арифметика денег, отказ от чисел с плавающей точкой и переполнений;
- инвариант бухгалтерии на 20 000 случайных операций и обнаружение подмены баланса;
- оплата ровно за новые рёбра, одна оплата на одну сигнатуру краша, штраф за ложный краш;
- отказ при повторе запроса, чужой подписи, подписи из другого домена, чужой лизе, истёкшей лизе, превышении лимитов, без залога;
- эскроу не уходит в минус: выплата урезается до остатка, кампания закрывается;
- 8 воркеров одновременно присылают одинаковые входы, и каждое ребро оплачивается один раз;
- реальная изоляция bubblewrap: только `lo`, `$HOME` не виден, окружение чистое, `/usr` только для чтения;
- полный цикл по HTTP; демо-фаззер находит оба заложенных бага.

**Не проверено в этой среде:** настоящие AFL++ и libFuzzer. Адаптеры `LibFuzzerEngine` и
`AFLPlusPlusEngine` протестированы на скриптах-имитаторах, которые создают те же каталоги
и имена файлов (`crash-*`, `queue/id:*`, `,orig:`). Разбор отчётов ASan и `afl-showmap` протестирован
на образцах в их реальном формате. Перед боевым запуском прогоните интеграционный тест на настоящих сборках.

## Чего здесь сознательно нет (это прототип)

- Хранилища: всё в памяти. Для работы нужен Postgres с журналом, в который только дописывают.
- Настоящих платежей: `POST /v1/admin/deposits` стоит на месте вебхука платёжного шлюза, вывода средств нет.
- TLS и ключей для каждого заказчика: админские вызовы защищены одним токеном.
- Отказоустойчивости координатора и распределённой проверки.
- Минимизации корпуса и сортировки крашей (одинаковые ли первопричины у разных сигнатур).
- Раздачи сборок воркерам: предполагается, что воркер получает бинарник, а sha256 сверяется с лизой.
