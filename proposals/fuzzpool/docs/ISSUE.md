## Что меня смутило

**1. PoW ничего не защищает**
Условие `(7n + 13) mod M = 0` (`internal/chain/retarget.go:64`) — линейное сравнение, оно решается формулой без перебора. Я проверил на вашем же `AppendPoHBlock` локально: узел принял 1000 блоков, решение заняло около 100 нс на блок, даже при `M = 10¹³`. Формула v2 (`mix64`) тоже обратима. Задача к тому же не зависит от хеша предыдущего блока и адреса майнера, поэтому историю цепочки она не защищает.

**2. Пул платит за заявленную мощность**
Выплата за попытки считается из `attempts` и `hashrate_gh_s`, которые присылает клиент (`cmd/coordinator/work.go:1997–2045`). Режим `PAYOUT_FOUND_ONLY` по умолчанию выключен. Баны по ID или IP помогают слабо: без залога новый ID ничего не стоит.

**3. Сеть централизована**
По `/api/status` и `/api/chain`: все последние блоки подписаны одним ключом, `peers: 0`, правило `first_valid_block_on_canonical_node_wins`.

**4. Стартовая эмиссия**
50 000 HMC при запуске — это около 91% всех выпущенных монет на сегодня. Клиенты платят за Dig/Hunt в HMC, то есть валютой, которую фактически контролирует оператор. Для B2B-клиентов и майнеров это риск и вопрос доверия.

**5. Фаззинг-пул: проверка выборочная, наказания нет**
Чистые прогоны Dig перепроверяются выборочно (Scan 1%, Audit 5%, Deep 40%), а пойманную подделку просто отклоняют, без штрафа. При такой доле проверок халтура выгоднее честной работы.

**6. Мелочи**
`float64` для сумм в API, адреса на 64 бита, установка через `curl | sudo bash`, `main.go` весит 181 КБ.

## Что предлагаю

Главная мысль: **воркер ничего не заявляет о себе, он присылает входные данные. Координатор сам их прогоняет и платит только за то, что измерил.**

- платить за **новое покрытие** (координатор прогоняет вход через `afl-showmap` и сравнивает с общей картой) и за **новые краши** (повтор дважды, дедупликация по сигнатуре стека), а не за «прогоны» и «попытки»;
- **залог воркера** и штраф за ложный краш вместо банов по ID;
- **без своей монеты**: заказчик кладёт USDT или фиат в эскроу, комиссия платформы видна отдельной строкой;
- деньги — целые микроединицы, бухгалтерия двойной записью с проверяемым инвариантом «сумма всех счетов = 0»;
- **bubblewrap** на обеих сторонах: у воркера, где запускается чужая цель, и у координатора, где проверяются чужие входы.

## Прототип

Чтобы не быть голословным, я собрал небольшой прототип на Go: около 2 800 строк, только стандартная библиотека, тесты проходят с `-race`. Архив `fuzzpool.zip` прикреплён к issue.

- `docs/HACKME_REVIEW.md` — подробный разбор: каждая проблема → решение → файл в прототипе;
- `go run ./cmd/demo` — честный воркер находит оба заложенных бага и получает оплату, а мошенник пробует 6 трюков (хешрейт, чужой корпус, повтор запроса, чужая подпись, чужая лиза, ложный краш), и все отклонены;
- есть адаптеры для AFL++ и libFuzzer. Честно предупреждаю: с настоящими движками я их не запускал, только со скриптами-имитаторами. Базы данных и реальных платежей в прототипе нет, это показ подхода, а не готовый продукт.
