# Разбор пула HackMe Network и предлагаемое решение

Разбор сделан по коду https://github.com/jokeez/hackme (коммит `8172145`, 2026-10-20)
и по открытым API hackme.tech на 2026-10-21. Ссылки вида `файл:строка` ведут на этот коммит.

Решение реализовано в прототипе `fuzzpool` из этого же архива (см. `README.md`).

---

## Часть 1. Проблемы

### 1. «Proof-of-Work» ничего не защищает
- Блок считается добытым, если для числа `n` выполняется `(7n + 13) mod M = 0`
  (`internal/chain/retarget.go:64`). Это линейное сравнение: оно решается одной формулой, без перебора.
- Проверка: узел HackMe, запущенный локально, принял 1000 блоков подряд,
  решение заняло около 100 наносекунд на блок. Подъём «сложности» до потолка `M = 10¹³` ничего не меняет.
- Формула v2 (`mix64(11n+17)`, включится на высоте 2 102 400) тоже обратима и решается так же быстро.
- В задачу не входят ни хеш предыдущего блока, ни адрес майнера, ни содержимое блока.
  Поэтому работа не защищает историю цепочки, даже если бы она была сложной.
- Видеокарты (CUDA/OpenCL, `internal/gpupoh/poh_search.cu`) перебирают задачу, у которой есть готовая формула ответа.

### 2. Пул платит за заявленную, а не за проверенную работу
- Выплата за «попытки» считается из полей, которые присылает сам клиент: `attempts` и `hashrate_gh_s`
  (`cmd/coordinator/work.go:1997–2045`). Проверить, что эти попытки были, нельзя.
- Режим «платить только за найденное» (`HACKME_COORDINATOR_PAYOUT_FOUND_ONLY`) по умолчанию выключен (`work.go:309`).
- Их собственный тест закрепляет такое поведение: `TestSubmitPrefersReportedHashrateOverWallGH`
  («coordinator should record reported GH/s»).
- Защита строится на эвристиках: потолок 128 GH/s, лимит на выплату за одну отправку, баны за
  «невозможную» частоту находок (`impossible_found_rate`, с пометкой «hdssh-style», то есть атаки уже были).
  Бан выдаётся по ID воркера или IP, а залога нет, поэтому новый ID обходит бан.
- Цифра «1.7 TH/s» на hackme.tech — сумма того, что майнеры заявили о себе сами.

### 3. Сеть централизована
Живые данные `GET /api/status` и `/api/chain`:
- все последние блоки подписаны **одним** ключом с одного адреса (`HMC-dfc143732a1fc3bc`);
- `peers: 0`;
- правило консенсуса: `first_valid_block_on_canonical_node_wins`, при расхождении
  `followers_stop_mining_and_reseed_from_canonical`;
- `chain_id: hackme-dev-mainnet`.

По сути это база SQLite одного оператора. Блокчейн в ней — оформление, а не механизм доверия.

### 4. Почти все монеты созданы при запуске
- При запуске создано 50 000 HMC на адрес оператора (`internal/block/genesis.go:11`,
  `internal/chain/economics.go: DevFeeAddress`).
- По `/api/status`: всего выпущено ≈ 54 741 HMC, значит, **91,3%** — стартовая эмиссия.
  Майнинг за ≈ 475 тыс. блоков дал ≈ 4 700 HMC.
- Ещё 70% сетевых комиссий и 5% платформенной комиссии с заказов уходят на тот же адрес.

### 5. Клиенты платят за фаззинг валютой оператора
- Пакеты Dig и Hunt оцениваются в HMC, заказы оплачиваются с HMC-кошелька
  (`orders_fund_api.go`, коммиты «Fund Orders from on-chain HMC»).
- Валюту, которой платит клиент, оператор фактически выпускает сам (пункты 1, 3 и 4).
- Биржа `exchange.hackme.tech` с хранением средств клиентов принадлежит тому же оператору и не лицензирована
  (так сказано в README). При этом описание репозитория («PAPER only: no custody») и README
  («HMC/SUP custody on public desk») противоречат друг другу. Серверная часть биржи не опубликована.

### 6. Фаззинг-пул: проверка выборочная, наказания нет
Сильная сторона проекта, но с оговорками:
- **Хорошо:** найденные краши перепроверяются всегда; прогоны Hunt (libFuzzer/AFL++) перепроверяются на 100%;
  есть «канарейки», то есть 2% заданий с подложенным багом (`internal/poolfuzz/canary.go`).
- **Плохо:** «чистые» прогоны Dig перепроверяются только выборочно: Scan 1%, Audit 5%, Deep 40%
  (`internal/poolfuzz/replay_policy.go`). Остальное принимается по порогам на заявленные
  `duration_ms` и `edges_touched` (`clean_floor.go`).
- Пойманную подделку просто **отклоняют**. Залога и штрафа нет, поэтому при 1–2% проверок
  халтура выгоднее честной работы.
- Платят за «прогон», а не за новое покрытие кода, хотя покрытие — главное, что получает заказчик.

### 7. Деньги и идентификаторы
- В API и расчётах выплат суммы хранятся как `float64` (`internal/chain/transfers.go:45`, `cmd/coordinator/work.go`).
  В базе используются целые единицы, и это плюс.
- Адрес — 16 hex-символов, то есть 64 бита (`internal/nodecrypto/ed25519.go:114`).

### 8. Установка и безопасность майнеров
- Установка предлагается через `curl https://hackme.tech/apt/install.sh | sudo bash`.
- Майнеры автоматически ставят AFL++ и clang и запускают цели заказчиков на своих машинах.
  Без строгой изоляции это раздача чужого кода на компьютеры участников.

### 9. Архитектура
- `main.go` — 181 КБ, `fuzz_campaigns.go` — 99 КБ, `pool.go` — 85 КБ; 117 Go-файлов в корневом пакете.
- ≈ 95 тыс. строк кода, 149 файлов документации, 273 shell-скрипта, один автор (три имени, один email).
- **Плюс:** проект собирается, `go vet` проходит без замечаний, тестов много.

## Часть 2. Решение (реализовано в прототипе `fuzzpool`)

### Принцип
**Воркер ничего не заявляет о себе, он присылает входные данные.
Координатор сам их прогоняет и платит только за то, что измерил.
Своей монеты нет.**

### Проблема → решение → где в коде

| # | Проблема HackMe | Решение в fuzzpool | Файл |
|---|---|---|---|
| 1 | PoW решается формулой и ничего не защищает | Майнинга нет. Вычисления — это сам фаззинг, а его результат проверяется | — |
| 2 | Платят за заявленный хешрейт | В протоколе нет полей хешрейта, попыток или времени. Неизвестные поля JSON отклоняются (HTTP 400) | `internal/protocol/protocol.go`, `internal/coordinator/http.go` (`decode`) |
| 2 | Бан по ID обходится новым ID | Лиза выдаётся только при залоге; не больше 4 живых лиз на воркера | `coordinator.go` (`Lease`) |
| 3 | Блокчейн одного оператора | Блокчейна нет. Есть журнал двойной записи с проверяемым инвариантом | `internal/ledger/ledger.go` |
| 4 | 91% монет создано при запуске | Монет нет. Деньги поступают только извне (оплата заказчика) и только туда выходят. Сумма всех счетов = 0, и это проверяется повторным проигрыванием журнала | `ledger.CheckInvariant`, `GET /v1/ledger/invariant` |
| 5 | Клиент платит валютой оператора | Оплата в обычной валюте (USDT или карта) в эскроу кампании. Комиссия платформы раскрыта и списывается отдельной строкой | `CreateCampaign` |
| 6 | Чистые прогоны проверяются выборочно, без штрафа | Платим только за **новое покрытие**: координатор прогоняет каждый вход через `afl-showmap` и сравнивает с общей картой. Прогона «без результата» не существует | `creditCoverageLocked` |
| 6 | Краши | Каждый краш прогоняется дважды, сигнатура должна совпасть; один баг оплачивается один раз | `replay`, `creditCrashLocked`, `target.Signature` |
| 6 | Подделку просто отклоняют | Ложное заявление о краше стоит залога, штраф уходит заказчику | `slashLocked` |
| 6 | Повторная отправка чужих входов | Новизна считается по общей карте покрытия: повтор даёт 0 | `coverage.Map` |
| 7 | `float64` для денег | `int64` микроединиц; в JSON только строки, число с плавающей точкой отклоняется | `internal/money/money.go` |
| 7 | Адрес 64 бита | ID воркера = полный SHA-256 от ключа Ed25519 | `internal/identity/identity.go` |
| — | Повтор и подделка запросов | Подпись Ed25519 с доменом и строго растущий nonce | `identity`, `authLocked` |
| 8 | Чужой код на машинах майнеров | bubblewrap на обеих сторонах: без сети, без `$HOME`, система только для чтения. Проверено тестом | `internal/sandbox/sandbox.go` |
| 8 | Подмена цели | sha256 каждой сборки закреплён в лизе; воркер откажется фаззить другую | `protocol.Lease.Builds`, `checkDigest` |
| 9 | Монолит | 9 пакетов, около 2 800 строк кода и 850 строк тестов | вся структура |

### Как выглядит поток

```
заказчик ──оплата──▶ эскроу кампании (5% платформе, видно в журнале)
воркер ──подпись + залог──▶ лиза: цель (sha256), цены, общий проверенный корпус
воркер: AFL++ / libFuzzer в песочнице ──входы──▶ координатор
координатор для каждого входа, в песочнице:
   падает дважды одинаково → новый баг? платим за краш
   заявлен краш, но не падает → штраф из залога
   иначе afl-showmap → новые рёбра? платим цена × рёбра
   иначе → 0
выплата из эскроу, не больше остатка; эскроу пуст → кампания закрыта
```

### Что проверено
`go test -race ./...` проходит. Демо (`go run ./cmd/demo`): честный воркер нашёл оба заложенных бага
и получил 45 из 95. Мошенник попробовал 6 трюков, и все отклонены:

| Трюк | Ответ |
|---|---|
| заявить `hashrate_gh_s` | HTTP 400 |
| отправить чужой корпус | 0 выплат |
| повторить подписанный запрос | HTTP 409 |
| подписать от чужого имени | HTTP 401 |
| сдать работу по чужой лизе | HTTP 403 |
| заявить ложный краш | −1 из залога |

### Чего в прототипе нет (честно)
- Не запускался с настоящими AFL++ и libFuzzer: адаптеры проверены на скриптах-имитаторах.
- Хранилище в памяти (нужен Postgres), нет реальных платежей и вывода средств, нет TLS.
- Координатор остаётся доверенной стороной. Подделку журнала оператором прототип не закрывает:
  нужна публикация хешей журнала или внешний аудит.

### Рекомендация автору HackMe
1. Убрать монету HMC, майнинг на видеокартах и биржу. Принимать оплату за фаззинг в USDT или картой.
2. Платить воркерам только за новое покрытие и новые краши, которые проверил координатор, а не за прогоны.
3. Ввести залог воркера и штраф за пойманную подделку.
4. Изолировать запуск чужих целей на машинах участников.
5. Разбить монолит на модули.

Фаззинг-часть HackMe — рабочая основа. Её стоит развивать отдельно от монеты.
